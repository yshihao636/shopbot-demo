一、问题与为什么用 Agent

电商客服的大部分工作量是重复问题，真正难的是「办事」：退款、取消、改地址要跨订单、物流、售后、风控多个系统判断，判断错了就是资损。

  • 重复问题占用 60% 以上的人工客服时间；高峰期排队 30 分钟以上，夜间无人响应。
  • 订单、退款状态在多个系统之间说法不一致，用户要反复找人工。
  • 不同客服的退款判断标准不统一，纠纷率高。

以上比例与时长是行业经验值，没有本平台数据。下面用公开的京东客服对话（CSDS）做代理基线。

二、用户与价值主张

一期聚焦两类人：想退货退款的买家，和处理转人工、审核退款的坐席。

售后用户（退货退款）人工坐席
谁已签收、想在退货期内退货退款的买家，含高价值会员和售后高频用户处理转人工会话和退款审核的坐席
要完成什么把钱退回来，并随时知道进度和下一步快速判断并处理真正需要人的会话和审核
现在怎么做在帮助中心找规则、排队等人工，反复描述订单和原因；各系统状态说法不一致大量时间回答重复查询；接手时要重新问用户
我们怎么做在对话里识别订单、补全原因和凭证，按售后规则说明审核方式，一次提交；进度页聚合售后、物流、支付状态查询由 Agent 处理；转人工附 AI 摘要；工作台一屏看到工单、摘要和订单
做完后7×24 提交申请，不重复描述，知道卡在哪一步工时集中在需要判断的会话上
替代方案自助售后页（规则分散、没有解释）、人工客服（高峰排队）。选 ShopBot 是因为一次对话办完，金额和时效都来自系统现有工单系统 + 人工全量处理
用什么衡量自动解决率、CSAT、退款纠纷率人工客服节省率、转人工率

一句话：售后用户不用排队、不用重复描述就能提交退款并看清进度；坐席只处理真正需要人判断的会话。

四、目标与衡量

北极星指标是自动解决率：只计 Agent 实际办完、用户没有再转人工的会话。其余指标是护栏，任何一项不达标都不能推进灰度。

五、关键判断

每条按「问题 → 判断 → 结果」写。这些都是我定下并能解释的规则。

1. 办事能力按风险分级，随灰度阶段放权

问题：一上来就让 Agent 退款，出错就是真金白银；但什么都不让它办，自动解决率到不了 40%（办理类占 32.9%）。

判断：产品版本和灰度阶段分开管。一项能力要同时满足「所属版本已发布」和「当前阶段已开放」才对用户可用。Phase 0–1 只开查询；Phase 2 开申请类；取消未支付订单等 L3 能力推进到 Phase 3 才开；改地址、取消已支付订单、执行退款等 L4 能力到 Phase 4 才由 Agent 执行。

结果：v0.1 只让 Agent 创建退款申请，审核仍走售后系统现有规则；Agent 执行退款放到 v0.4，且仍需用户确认 + 风控 + 人工审核。

2. 把「提交」从模型手里拿走

问题：红队提示注入用例中，模型 3 次都没展示确认卡就直接提交了伪造的卡号。

判断：模型的越界倾向是稳定的，靠提示词约束不可靠。把提交工具从模型的工具里移除，改由后端在用户点击确认卡后执行。

结果：修复后不再出现提交尝试。担心的是「安全了但办不成事」，所以单独测了提交方式的影响：同一提示词下只改提交方式，端到端成功率 89.29% → 96.43%，配对区间 [0, +16.7]，下限贴着 0，我只写「没有降低成功率」，不写「提升」。附带收益：确认后少一轮模型调用，每个任务费用低 27%、耗时少 1.9 秒。

3. 说转人工，就必须真的转

问题：大额补偿用例里，Agent 5/12 次回复「为您转人工」，实际没有调用转人工。用户以为有人在处理，工单其实不存在。

判断：把「口头承诺必须对应真实动作」写成规则，并加进评测项。

结果：红队回归集 12/12、留出集 6/6。但端到端评测里每个版本仍有 1 次回复「正在为您转接人工客服」却没有调用转人工，提示词修补没有完全消除这个问题。下一步由后端核对「回复声称已转人工」和转人工调用记录，不一致就替换回复。

4. 取消订单的自动执行阈值单独设为 ¥5,000

问题：如果沿用退款的 ¥500 阈值，大部分家具、家电订单的取消都要转人工。

判断：已支付未发货的取消没有货物流出，原路退款，欺诈风险远低于退货退款，所以单独设阈值。

结果：低于 ¥5,000 二次确认后执行，达到阈值走人工审核。

5. 「拣货中」的订单不承诺能取消

问题：仓库已经在拣货，订单不一定截得住。直接说「已取消」，就可能出现「已取消却发货」，比转人工更伤信任。

判断：订单系统有受控拦截能力时才先尝试拦截，拦截成功才告知已取消并退款；不能拦截或结果不确定时，创建取消申请，明确说不保证成功。

结果：确认卡上提前写明这一点；只收到「拦截已受理」时不说已取消。

6. 金额以系统为准，审核原因分情况说

问题：用户会说「退我 500」；需要人工审核时，用户想知道为什么。

判断：退款金额只认售后系统返回的本次可退金额，不采纳用户口述。审核原因分两类说：金额超过自动审核阈值的，可以直接说明，用户能理解；风控命中、退款次数超限等其他原因，统一说「需进一步核实」，不教人怎么绕过规则。

结果：系统没有返回可退金额时不出确认卡；超阈值的申请必须上传凭证，给审核员留依据。

六、方案与原型

一次退款请求怎么走

  1. 识别意图：退货退款
  2. 校验身份与订单归属
  3. 补全原因与凭证
  4. 售后规则返回审核方式
  5. 确认卡（金额取系统可退金额）
  6. 用户点击确认，后端提交
  7. 结果卡：售后单号与进度

第 4 步返回「需人工审核」：确认卡标明需人工审核并说明原因（见判断 6）；提交后，服务时间内带 AI 摘要转人工，时间外告知结果会通过站内信通知；坐席在工作台只写回审核结果，由系统通知用户，不在对话里替用户发确认卡、不承诺到账时间。

出了问题怎么兜底

  • 业务系统失败：不编造结果，不声称申请成功，降级或转人工。
  • 重复点击：同一张确认卡只执行一次，已有进行中的售后单时返回当前进度。
  • 多个系统数据对不上：不替用户判断，转人工核实。
  • 高风险误操作告警（P0）：自动打开「关闭执行能力」，Agent 只保留问答和查询，1 分钟内生效。

八、我改过的判断

需求不是一次写对的。下面是我推翻过自己的地方，以及为什么改。

规则原来现在为什么改
超阈值退货的凭证¥500 以上无理由退货不强制凭证，靠仓库验货兜底超过自动审核阈值时必须上传超阈值的申请会进人工审核，审核员没有凭证就没有判断依据
人工审核的原因一律不解释，只说「需人工审核」金额超阈值可直说，其他原因统一说「需核实」金额阈值不是风控秘密，说清楚能减少用户追问；风控规则仍不暴露
拣货中取消先拦截再取消，失败转退货有受控拦截能力才尝试，结果不确定就建申请、不承诺原写法默认一定能拦截，但订单系统不一定有受控拦截能力；结果不确定时承诺取消，风险比转人工更大
坐席审核之后坐席审核通过后，在对话里给用户发确认卡坐席只写回审核结果，由系统通知用户审核和用户确认是两件事；审核结果写回系统后由系统通知，避免坐席在对话里代替系统推进业务动作
人工抽检每天固定 50 条，按来源比例抽按灰度阶段比例抽 + 必抽项 + 每日不足 50 条时补足放量阶段越早风险越高，抽检比例要跟着灰度走；低分、差评、投诉必须看

版本做什么

v0.2投诉申诉工单、取消未支付订单、商品咨询、知识库、LLM 自动评分、催发货与签收争议工单
v0.3换货补发维修、优惠券与价保申请、发票、账户与隐私请求、改地址、取消已支付未发货订单
v0.4Agent 执行退款、价保退差价、补偿券、坐席绩效、AB 实验
v0.5复杂售后（跨境、平台仲裁、大额退款人机协同）、App 以外的渠道

所有版本都不做：商家入驻与店铺运营、广告投放、法律结论性答复、竞品评价；账户注销、删除数据只建专岗请求，不自动执行。

局限与下一步

  • 没有真实流量：自动解决率、转人工率、CSAT 只能在灰度阶段测。
  • 真实对话准确率 88.1%，低于 90% 目标：先用本平台流量复核，再决定是否加样本或改提示词。
  • 转人工类任务最弱：健康必转已补路由和后端拦截，下一步验证独立表达、误转率、实际队列及其他转人工动作一致性问题。
  • 业务系统接口、值班负责人、生产阈值和成本预算未确认：没有补齐的能力不进入灰度。
